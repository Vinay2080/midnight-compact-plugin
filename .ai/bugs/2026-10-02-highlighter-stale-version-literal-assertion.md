# Stale Version Literal Assertion After Lexer Double-Advancement Fix

- **Date:** 2026-10-02
- **Feature / Component:** highlighter / test
- **Severity:** Medium
- **Status:** Resolved

## Symptoms

Running `./scripts/verify-patch.ps1 -AllTests` failed at Gate 3 with:
```text
CompactHighlightingTest > testDeclarationHighlighting FAILED
    junit.framework.AssertionFailedError: Expected text '20.0' to be highlighted with COMPACT_VERSION, but was not. All highlights: ['language_version':COMPACT_PRAGMA, ' ':null, '0.20.0':COMPACT_VERSION, '/// Documentation for contract':COMPACT_DOC_COMMENT, ...]
    at CompactHighlightingTest.java:348
```

## Context

In commit `688cf62` (documented in `.ai/bugs/2026-10-01-lexer-bad-character-double-advancement.md`), `CompactLexer` was patched to prevent unrecognized characters (`@`, `~`, `^`, etc.) from double-advancing the buffer offset and swallowing the subsequent character. Verification for commit `688cf62` was executed using scoped test patterns (`dev.verloren.midnight.lexer.*` and `CompactArchitectureTest`), so `CompactHighlightingTest` was first re-evaluated on GitHub Actions CI.

## Root Cause

In `src/test/java/dev/verloren/midnight/highlighter/CompactHighlightingTest.java`, `testDeclarationHighlighting` declared:
```compact
pragma language_version ^0.20.0;
```
Prior to commit `688cf62`, the unrecognized character `^` hit the `default:` branch of `CompactLexer.advance()` without a `return;` statement, falling through into a second `finishHelper(CompactTokenTypes.BAD_CHARACTER)` call. The second call consumed the leading `'0'` character of `0.20.0`. The remaining text `.20.0` was then lexed as a dot and a `VERSION_LITERAL` of `"20.0"`.

When `CompactHighlightingTest` was authored in commit `81ba062`, the author asserted:
```java
assertHasHighlight(highlights, "20.0", CompactHighlighterColors.VERSION);
```
expecting the corrupted token text produced by the lexer bug.

Once commit `688cf62` resolved the double-advancement bug, `'0'` was no longer swallowed, and `CompactLexer` emitted the full, correct token `"0.20.0"` with token type `VERSION_LITERAL`. Consequently, semantic highlighting highlighted `"0.20.0"` with `CompactHighlighterColors.VERSION`, rendering the assertion for `"20.0"` stale and causing CI to fail.

## Investigation

1. Inspected test report `build/test-results/test/TEST-dev.verloren.midnight.highlighter.CompactHighlightingTest.xml`, confirming that `'0.20.0':COMPACT_VERSION` was generated by the highlighter.
2. Traced git history of `CompactHighlightingTest.java` and `CompactLexer.java` using `git log -S "20.0"` and commit `688cf62`.
3. Verified that `CompactLexer` correctly tokenizes `0.20.0` into a single `VERSION_LITERAL` covering the entire semver string, and that `CompactHighlightingAnnotator` and `CompactSyntaxHighlighter` correctly attribute `CompactHighlighterColors.VERSION` to that token.

## Solution

Updated `src/test/java/dev/verloren/midnight/highlighter/CompactHighlightingTest.java`:
- Changed `assertHasHighlight(highlights, "20.0", CompactHighlighterColors.VERSION);` to `assertHasHighlight(highlights, "0.20.0", CompactHighlighterColors.VERSION);`.
- Verified file size remains $\le$ 400 lines (351 lines).

## Prevention / Lesson

Whenever foundational lexical or parser tokenization bugs (such as character advancement or token boundary defects) are resolved, always execute the full automated verification harness (`-AllTests`) across all downstream subsystems (highlighters, inspections, intentions, completions) to catch assertions that were previously calibrated against corrupted token streams.
